# Контракт данных ЧМЭ3 / ЧМЭ3Т

## Цель

Пакет должен быть пригоден для последующей интеграции в `Атлас`, `Диагностику`, `Приёмку` и офлайн-ассистент без повторной ручной классификации происхождения информации.

Главное правило: **официальность источника не равна истинности, а полезность практического способа не равна разрешению на его выполнение**.

## Обязательные поля утверждения

Каждая самостоятельная техническая сущность, диагностический шаг, приёмочный пункт или конкретное значение должна иметь:

- `id` — стабильный ID;
- `applicability` — серия/модификация/исполнение;
- `evidenceRefs` — ссылки на записи `source_registry.json`;
- `evidenceStatus` — статус подтверждения;
- `confidence` — уверенность именно в корректности факта;
- `actionAuthority` — можно ли использовать сведения как основание для эксплуатационного действия;
- `assistantTerms` — технические и разговорные поисковые формы, если они специфичны для сущности;
- `conflictRefs` — явные ссылки на конфликтующие сведения, если они обнаружены.

## Evidence status

- `996R_CONFIRMED` — положение найдено в проверенной актуальной редакции 996/р.
- `OFFICIAL_OTHER` — подтверждено другим действующим нормативным документом.
- `MANUFACTURER_CONFIRMED` — подтверждено заводским РЭ, схемой, инструкцией изготовителя либо иной проверенной документацией конкретного исполнения.
- `LOCAL_INSTRUCTION` — местный порядок; обязательна географическая/организационная область действия.
- `TRAINING_REFERENCE` — учебник, пособие, техническая публикация. Может хорошо объяснять устройство, но само по себе не разрешает действие.
- `FIELD_PRACTICE` — подтверждённая эксплуатационная практика без достаточного нормативного основания.
- `CONFLICT` — существует содержательное расхождение между источниками.
- `UNVERIFIED` — материал найден, но происхождение, применимость или корректность ещё не проверены.
- `HISTORICAL_SUPERSEDED` — ранее действовавший материал, утративший нормативную силу.

## Action authority

Статус достоверности и допустимость действия разделяются.

- `SOURCE_BOUND_OK` — действие имеет достаточное подтверждённое действующее основание и прошло проверку применимости.
- `INFORMATION_ONLY` — сведения можно показывать для понимания/локализации, но не выдавать как команду к выполнению.
- `REQUIRES_PROFILE_CHECK` — сначала надо подтвердить модификацию/исполнение.
- `REQUIRES_LOCAL_RULE` — решение зависит от местной инструкции/депо/условий работы.
- `REQUIRES_CONFLICT_REVIEW` — найдено расхождение; действие блокируется до разбора.
- `PROHIBITED_OR_UNSAFE` — способ известен, но не должен предлагаться как действие пользователю.

## Конфликты

Нельзя автоматически считать более новый документ технически более полным, а нормативный документ — более точным описанием устройства.

Для каждого конфликта фиксируются:

1. что именно утверждает каждый источник;
2. к какому исполнению относится утверждение;
3. даты/редакции;
4. различается ли описание устройства или только допустимый порядок действий;
5. какое представление допустимо в Атласе;
6. какое действие допустимо в Диагностике.

Практический способ может остаться в базе даже при конфликте с нормативным порядком, но только как `FIELD_PRACTICE`/`CONFLICT` и без автоматического разрешения к выполнению.

## Атлас

Минимальная сущность оборудования:

```json
{
  "id": "CHME3-EQ-...",
  "name": "...",
  "aliases": [],
  "driverSlang": [],
  "systems": [],
  "location": {},
  "purpose": "...",
  "principle": "...",
  "normalState": [],
  "deviationSigns": [],
  "relatedIds": [],
  "schemeRefs": [],
  "diagnosticRefs": [],
  "applicability": [],
  "evidenceRefs": [],
  "evidenceStatus": "...",
  "confidence": "...",
  "actionAuthority": "INFORMATION_ONLY",
  "assistantTerms": []
}
```

Схемы должны ссылаться на те же ID оборудования, а не заводить отдельные несвязанные названия.

## Диагностика

Диагностический сценарий хранит отдельно:

- наблюдаемый симптом;
- немедленные безопасные действия;
- профиль/исполнение;
- различающие вопросы;
- проверки и ожидаемый результат;
- вероятные причины;
- допустимые действия;
- недопустимые действия;
- условия прекращения поиска;
- поля доклада;
- нормативный маршрут (если есть);
- дополнительные заводские/учебные/полевые ветви;
- конфликт с нормативным порядком, если есть.

Полевая ветвь **не смешивается** с 996/р в один безымянный алгоритм.

## Приёмка

Пункт приёмки должен различать:

- обязательный нормативный/руководственный минимум;
- расширенный эксплуатационный осмотр;
- местные проверки;
- вариантные проверки для ЧМЭ3/ЧМЭ3Т/ЧМЭ3Э;
- переход в диагностику при обнаружении признака неисправности.

## Ассистент

При наполнении любой сущности одновременно проверяются:

1. техническое название;
2. заводское/схемное обозначение;
3. распространённое сокращение;
4. разговорное название;
5. формулировка симптома обычной речью;
6. возможная ASR-форма;
7. противоположные состояния, которые нельзя схлопнуть (`не выключается` / `сам выключился`).

Новые термины сначала попадают в `search_vocabulary.json` с указанием происхождения. В движок ассистента они переносятся после проверки на ложные совпадения.

## Критерий готовности пакета

ЧМЭ3/ЧМЭ3Т считается готовым к пользовательской приёмке только когда:

- закрыта основная номенклатура оборудования и систем;
- схемные сущности связаны с оборудованием;
- диагностические сценарии покрывают доступный 996/р и значимый дополнительный материал;
- полевая практика размечена отдельно;
- приёмка собрана в маршруты;
- словарь ассистента покрывает специфичные термины и реальные разговорные запросы;
- все ID/ссылки/источники проходят автоматическую валидацию;
- нерешённые конфликты перечислены явно.
